## 一、要解决的核心问题

| 数据 | 实测值 |
|---|---|
| 门店菜单餐品数（柏联广场） | 113 |
| `list-nutrition-foods` 营养库 | 158 条 |
| **名称精确匹配率** | **19 / 113 = 17%** |

失败原因：营养库是**单品名**（巨无霸），菜单大量是**套餐名**（巨无霸三件套）。

- 不拆轮次 → 算不出套餐真实营养
- 拆轮次 → 113 个餐品 = 113 次 `query-meal-detail`，撞 600 次/分钟限流

**解法：本地枚举 → 硬约束过滤 → 只对Top-K 调 MCP。**

## 三、★ 价格预测与官方算价完全一致

用`calculate-price` 接口验证求解器的输出：

| | 价格 |
|---|---|
| 求解器静态计算（base 3750 + diffPrice −¥1） | **3650 分** |
| 官方 `calculate-price` 返回 | **3650 分** |

**完全一致。**

这条验证的意义：静态 `diffPrice` 可以直接参与求解，
**只有最终展示给用户前才需要调算价做最终确认**——
这把必须调用的接口数从「组合总数」压到「候选数」。

### diffPrice 实测值

```
轮次2  中薯条         + ¥0
轮次2  小杯玉米杯     − ¥1     ← 唯一减价项
轮次3  可乐中杯+ ¥0
轮次3  无糖可口可乐中杯  + ¥0     ← 与可乐同价的零糖选项
```

## 四、代码里处理的六个实测坑

| # | 坑 | 处理方式 |
|---|---|---|
| 1 | `list-nutrition-foods` 是**双层嵌套** | 先剥外层 JSON，`data` 字段才是 TOON |
| 2 | 价格单位不一致 | 菜单「元」字符串 / 算价「分」数字 → 内部统一用**分** |
| 3 | `roundList` 字段名是 `round` 不是 `roundId` | 从 `inputSchema` 逐字读，不凭直觉命名 |
| 4 | `searchType=1` 新账号返回空 | 必须 `searchType=2` |
| 5 | 营业时间 46.7% 是默认值污染 | `is_real_business_hours()` 剔除 `00:00~23:59` |
| 6 | `distance` 不是米、经纬度恒 0 | **不用它做就近排序** |

### 还有两条防御性设计

**① 查不到营养的组合直接丢弃，不给假数字**

```python
if unresolved:
    continue   # 宁可少推荐，也不用估算值凑数
```

**② 去料策略不臆造扣减数值**

吉士、酸黄瓜等 `modification` 项去掉能省多少热量，
需要官方数据支撑。在没有实测数据前，只记录「去掉吉士」这个决策，
**不编造「省 45 千卡」这种数字**。

## 六、合规表述

代码里的目标类命名为 `Goal`，模式字段为
`balanced` / `high_protein` / `low_sodium`，
**刻意不用「减脂」「增肌」「瘦身」**。

原因：官方 `CONTEST_DECLARATION.md` 原文写明
「项目输出仅供参考，**不构成医疗、营养或其他专业建议**」。

所以定位是「**帮你按自己的偏好挑**」，不是「帮你制定饮食方案」。
输出末尾必须附此声明。
