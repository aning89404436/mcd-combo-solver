## 一、工具清单：35 个（文档写 33个，多2 个）

实测 `tools/list` 返回 35 个。多出来的是：

|工具 | 说明 |
|---|---|
| `query-survey-coupon` | 订单调研券（入参 orderId）|
| `query-promotions` | 门店促销信息 |

⚠️ 官方 README 与实际接口**不同步**，做项目时以实际返回为准。

### 参数陷阱：`beType` 和 `orderType` 是两套东西

这是官方文档表述最含糊、最容易踩的地方：

| 参数 | 取值 |
|---|---|
| `orderType` | 1 = 到店（含到店自取 + 得来速）｜ 2 = 外送（含麦乐送 + 企业团餐）|
| `beType` | 1 = 到店取餐｜ 2 = 麦乐送到家｜ 5 = 得来速｜ 6 = 企业团餐 |

**注意 `beType=2` 是「麦乐送到家」，而 `orderType=2` 才是「外送」范围。** 两者交叉，不是简单包含关系。

`beCode` 规则：**得来速(5) / 外送 / 团餐 必传，到店自取(1) 不传。**

## 二、`list-nutrition-foods` 返回结构（关键）

### 官方文档没说的第一层：响应是「双层嵌套」

实际返回不是 TOON 文本，而是：

```
# API Response Information
...（字段说明）...
## Original Response
{"success":true,"code":200,"data":"[160]{...}:", "datetime":..., "traceId":...}
```

**`data` 字段本身才是 TOON 字符串。** 所有实战教程都直接当 TOON 解析，会报错。

### TOON 格式

```
[160]{productName,nutritionDescription,energyKj,energyKcal,protein,fat,carbohydrate,sodium,calcium}:
  猪柳麦满分,null,1288,308,16,16,24,781,213
  猪柳蛋麦满分,null,1618,387,23,21,25,846,243
  中薯条,null,1210,289,4,12,38,165,18
```

- **实测 158~ 160 条**（两次调用条数有微调，头部声明数与实际行数一致）
- 9 个字段
- `nutritionDescription` **本批160 行全部为 `null`**
- 实测**每行恰好 8 个逗号**，无一行例外

### 关于「值可能自带逗号」

网上教程警告 `nutritionDescription` 可能自带逗号、不能按位置 split。
**实测本批数据不成立**（全 null），但仍应写防御性解析 —— 官方随时可能补描述文本。
`toon_parser.py` 按「行内逗号数 == 字段数-1」校验，不匹配则降级为该行跳过并告警。

## 三、门店查询：死路与真路

### `searchType=1` 在无收藏账号上是死路

```json
{"success":false,"code":600050,"message":"收藏餐厅列表为空，请您提供城市+关键词进行搜索"}
```

**即使传了 city + keyword 依然报这个错** —— 因为 searchType=1 查的是「我的收藏门店」，
新账号无收藏，必然为空。传 6 个关键词全部复现此错。

### `searchType=2` 才能按位置搜

```
{"beType":1,"searchType":2,"city":"昆明","keyword":"西山区"}  → 成功
```

### 昆明实测：30 家门店

### 数据缺陷 1：`distance` 不是米

「麦当劳昆明滇池后海餐厅」返回 `distance: 2526`，而滇池后海在昆明西侧。
数值像厘米或异常值，**不是米**。且 `longitude/latitude` 全为 `0.0`。

**结论：不能用距离做「就近推荐」的排序依据。**

### 数据缺陷 2：营业时间是默认值污染

30 家中 **14 家**返回 `businessStartTime: "00:00"` / `businessEndTime: "23:59"`，
占 46.7%。这是**数据缺失被填成默认值**，不是真的全天营业。

反例很明确：`麦当劳昆明圆通山餐厅` 返回 `10:00-18:00`（午市餐厅），
`麦当劳昆明云纺餐厅` 返回 `07:30-23:59`。

**如果拿`00:00-23:59` 当「全天可点」，会给用户完全错误的推荐。**
任何做「现在能不能点」的逻辑，都必须先识别并剔除这类脏数据。

## 四、菜单结构

`query-meals` 返回 `data.categories[15]` + `data.meals{113}`（柏联广场店）。

- `meals` 是 **dict，key 为餐品编码**
- 单品结构：`{name, image, currentPrice, originalPrice, canWithOrder}`
- **实测 `currentPrice` 是字符串「元」**，如 `"33.5"`（与教程一致）
- 分类名内含 `\n`（如 `"鸡肉汉堡\n/卷"`），解析时需`strip().replace('\n','')`

### 重大发现：官方已在推「500 大卡套餐」

菜单第 13 个分类的真实名称是 `"500\n大卡套餐"`，标签「粉丝之选」。

**这改变了项目定位判断** —— 热量/卡路里叙事是麦当劳自己在推的品牌方向。
市面上的营养类项目如果在「教育用户少吃麦当劳」，是在和官方品牌叙事对着干，
既有合规风险，也缺乏说服力。

**转向：「帮你在麦当劳吃对」，而不是「帮少吃麦当劳」。**

## 五、★核心卡点：营养数据与菜单无法直接对齐

### 匹配率实测

| 方式 | 命中 |
|---|---|
| 名称精确匹配 | **19 / 113 = 17%** |
| 去后缀模糊匹配 | 39 条 |

失败原因很直接：**营养库是单品名，门店菜单大量是「套餐名」**。

```
菜单：麦辣鸡腿汉堡三件套 ¥33.5     营养库：麦辣鸡腿汉堡✓
菜单：巨无霸三件套        ¥37.5     营养库：巨无霸      ✓
菜单：板烧鸡腿堡三件套      ¥34.5     营养库：板烧鸡腿堡✓
```

**94 个套餐需要先拆轮次才能算营养。** 这就是所有同类项目的天花板 ——
不拆轮次，只能给单品热量；拆轮次，113 个餐品意味着 113 次 API 调用，
撞上 600 次/分钟限流。

## 六、★`query-meal-detail`：真正的差异化抓手

`query-meal-detail` 能拿到套餐完整结构 `rounds[] → choices[]`，
每个 choice 带`diffPrice`（加价）和 `modification`（特制项）。

### 实测：巨无霸三件套（9900005466，¥37.5）

**轮次 1 · 新升级巨无霸**（必选 1）
- 巨无霸 `+¥0` **可特制：巨无霸酱 / 吉士 / 生菜 / 酸黄瓜 / 洋葱粒**

**轮次 2 · 选择套餐内小食**（必选 1）
| 选项 | 加价 |
|---|---|
| 中薯条 | +¥0 |
| 脆脆薯条 / 大薯条 | +¥2 |
| 5 块心形薯饼 + 韩式辣椒黄油风味酱 | +¥1 |
| 马来咖喱风味薄皮肉骨鸡 3 块 | +¥2.5 |
| **小杯玉米杯** | **−¥1**（唯一减价）|
| 大杯玉米杯 | +¥1.5 |

**轮次 3 · 选择套餐内饮料**（必选 1，共 21 项）
| 选项 | 加价 |
|---|---|
| **无糖可口可乐中杯** | **+¥0**（同价无糖）|
| 可乐中杯 / 雪碧中杯 / 阳光柠檬红茶中杯 | +¥0 |
| 可乐大杯 / 无糖可口可乐大杯 / 雪碧大杯 | +¥2 |
| 100% 苹果汁 / 中杯怡泉+C | +¥1.5 |
| 麦咖啡™ 冰/热奶铁中杯 | +¥11 |
| 大杯鲜萃咖啡（可加奶油球、白砂糖）| +¥2 |

### 这个数据意味着什么

1. **小杯玉米杯是唯一能减价的选项**（−¥1），且热量远低于薯条
2. **无糖可乐与可乐同价**（都是 +¥0）—— 零成本减糖
3. **去吉士省约 45 千卡**，且不加钱（modification 里price 均为 0）

**这三个抓手全都必须调 `query-meal-detail` 才能知道，且没有任何静态资料能预知。**
这正是「让模型挨个试错」必然撞限流、而「本地先算」能解决的问题。

## 九、限流与请求预算

- 限流：**600 次/分钟**，超限 429
- 401 = Token 无效/过期/未提供

### 本项目的请求预算设计

以单次推荐计算：

| 步骤 | 调用次数 |
|---|---|
| 查询附近门店 | 1 |
| 查询菜单 | 1 |
| 查询参与候选套餐的详情 | **N（关键项）|
| 对 Top-K 候选算价 | **K** |

**绝不能对 113 个餐品全部调详情再全量算价。**
正确做法：本地枚举组合 → 按营养/预算过滤 → 只对 Top-K 调详情与算价。

## 八、⚠️ 价格单位陷阱（高危，必须实测）

### 实测对照

`query-meals` 返回 `currentPrice: "26.5"`（**元，字符串**）
`calculate-price` 返回 `price: 2650`（**分，数字**）

**同一份巨无霸，菜单显示 ¥26.5，算价返回 2650。**

如果直接把 `calculate-price` 的返回值展示给用户，**价格会变成 100 倍**。

### ★ 端到端对照验证（本项目最有说服力的数据）

| 配置 | 算价结果（分） | 折算 |
|---|---|---|
| 巨无霸三件套 + 中薯条 + 可乐 | 3750 | **¥37.50** |
| 巨无霸三件套 + **小杯玉米杯 + 无糖可乐** | 3650 | **¥36.50** |

**省¥1，且热量更低、糖为零。** 这组数据由官方实时算价接口验证，
证明静态 `diffPrice`（小杯玉米杯 −¥1）准确可信。

→ 可直接作为 README 的核心卖点：**同样的钱，更好的搭配**，数据来自麦当劳官方接口。

## 九、⚠️ `calculate-price` 的 `roundList` 字段名坑

### 错误示范（会返回 500）

```json
{"items":[{"productCode":"9900005466","quantity":1,
  "roundList":[{"roundId":2,"comboItemList":[...]}]}]}
```

### 正确写法

```json
{"items":[{"productCode":"9900005466","quantity":1,
  "roundList":[{"round":"2","comboItemList":[{"code":"4437","quantity":1}]},
               {"round":"3","comboItemList":[{"code":"3071","quantity":1}]}]}]}
```

**三个要点：**
1. 字段名是 **`round`（字符串）**，不是 `roundId`（数字）
2. `round` 的值对应 `query-meal-detail` 返回的 `rounds[].id`，**但类型是字符串**
3. 轮次选项的 `code` 必须来自 `query-meal-detail` 的 `choices[].code`，
   **不能用单品编码，也不能猜**（我猜的 4642/1002 是错的，直接 500）

### 500 错误的排查方法

官方对错误字段名**不返回参数校验错误，直接 500「服务器发生了未知的问题」**。
所以任何 `calculate-price` 失败都应优先怀疑：
1. `round` 字段名或类型错
2. `code` 来自猜的而非 `query-meal-detail`
3. 缺少必填的 `storeCode` / `orderType` / `beType`
